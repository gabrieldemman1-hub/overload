### Where the spec was unclear or wrong, and what was done

- SPEC 3.6 read literally ('when the phone holds one, it is carried across') makes the safety copy of Remove useless in 3.0: after Remove the phone still holds an old food copy (state.food and deleted.food, with an empty diary), so a literal carry would put the empty diary over the diary of the copy 'Before removing the old food log'. I carry per part: state.food when the phone has any saved food, meal or target; state.diary with deleted.food when the phone has any food day; otherwise the file's part is used. Evidence: tests/train-replace.js 'restore after Remove' (stored text is the fixture again) and the two cases asked for (food present: byte for byte kept; empty phone: the file's). Please confirm this reading.
- SPEC 3.5 'Only offered after a copy or file was made on this phone': I made it stricter. Remove is offered and accepted only while the last copy or file has the same hash as what is on the phone now. Otherwise food logged after the copy (v2.8 running again during a half-arrived update) could be removed without ever having been copied. Tested in train-handover.js.
- SPEC 3.5 does not say what happens when the safety copy cannot be stored (IndexedDB not answering). I chose: nothing is removed, with the message 'The safety copy could not be stored, so nothing was removed. Try again.' In a browser where IndexedDB never works, the old food log can therefore not be removed.
- SPEC 3.2/3.4 'Record split.at' before the first save: I write split.at only once the copy is known to be stored (a few ms after the start), because the first start after an update reloads within seconds and backup.js can fail to open IndexedDB. If the copy was not stored, the next start takes it from the text stored then (3.0 has not changed food in between) and a copy already there is never written over. The raw text itself is still the one read before the first save. On a new install split.at is written at once and no copy is taken.
- SPEC 3.4 shapes: 'dismissed' holds the food hash at the moment of hiding (a text), so the card can return when the food copy changes; 'removed: { at }' has no hash, so 'removed' counts only while the diary is empty (days appearing again bring the card back). The hash covers state.food and state.diary but not deleted.food: those records drop out by themselves after 90 days and would make the card come back with nothing changed.
- Not in SPEC 3.5 but in state.md hazard 6c: on Remove I also delete the removed days from overload.sync.v1.days. The patched sync.js does the same at its next push; my edit covers the case where sync.js is not loaded at that moment (the Firebase files are not cached on the first starts) and v2.8 runs next, which would otherwise delete those days in the account. Say so if app.js should not touch that note.
- offline.md 1.7 describes the 8 s 'still starting' note as something the owner reads. In Chromium the stylesheet swap that lets the note draw also unblocks the scripts, so the app starts at once (unstyled until the stylesheet arrives) and the note is seen only for an instant. This is v2.8's behaviour too. With a second stylesheet, v2.8's logic (first link only) left the app unstarted; shown in a scratch run and covered by train-rescue.js 'slow start'.
- fixtures.md says 'node tests/smoke-v28.js' checks the fixtures; it serves the repo itself, which is now 3.0, so run from the repo it fails by design (no Food tab). I ran it against v2.8 by copying tests/ into the extracted v2.8 folder: 73 of 73 pass.
- The full card on Today is tall: about 575 px of the 844 px screen at 390 px wide, so Start workout is below the fold until the card is hidden or the log copied. SPEC 3.3 asks for the same offers on Today, so I kept them; the restyle step may want a shorter Today version.

### Where the spec was unclear or wrong, and what was done

- Appendix A lets v2.8 delete the whole cloud food log in one sequence. It forgets vanished days only inside push(), which needs a signed-in user. Signed out (the note is kept on purpose), remove the diary on 3.0, then v2.8 starts and signs in: v2.8 deletes every day the note still lists. Reproduced with Appendix A exactly as given (git-applied copy), small fixture: 'writes: 4: delete foodDays/2026-11-15, delete foodDays/2026-11-18, delete foodDays/2026-11-20, delete foodDays/2026-11-21'. Fixed in sync.js by forgetting at every save; the test 'v2.8 deleted no food day in the cloud' covers it.
- Appendix A, second hole: push() took its rollback copy of the note before forgetting days, so a refused batch (rules, quota) wrote the forgotten days back into overload.sync.v1 until the retry 60 s later. A v2.8 start in that window deletes them in the cloud. Shown by putting the two lines back in Appendix A's order: the check 'the food days stay forgotten after the roll-back' fails. Fixed by forgetting first.
- 'Byte-identical food part' (SPEC 8, sync.md hazard 1) holds for what 3.0 writes, not for the cloud's state afterwards when a v2.8 phone is on the account: v2.8 sorts its deletion records whenever a core arrives and sends the core again, so the text of deleted.food changes by v2.8's own doing. Observed in the two-phone run. The tests therefore compare the food part inside each core 3.0 wrote with the core the cloud held just before it (30+ cores per run, 0 differing).
- Not fixed, by reasoning only (the fake cannot show real SDK timing): mergeCore's localAhead is computed with the phone's own food when the first core snapshot of a session already differs from the note (nothing cached). If the phone's food differs from the cloud's (second device on v2.8, or a phone first linked on 3.0), the phone counts as 'ahead' and its weigh-in or night for a date both sides have wins over the cloud's. With the SDK's persistent cache the cached copy normally arrives first and this does not happen.
- Not fixed, by reasoning only: with includeMetadataChanges false, a known phone that starts offline on an account that has no core document is never told 'the server has none', so it does not upload its core in that session (it does on the next start with signal). Also, a known phone never repairs a core document whose core is not text: it waits for a readable core before sending. Both err on the side of not writing.
- The command in the task text to extract v2.8 fails: 'git archive 3b17963 | tar -x -C <dir> .' gives 'tar: .: Not found in archive' and extracts nothing. Without the trailing dot it works; both tests use that form.
- bump.sh fails when fuel/sw.js exists and lists a file that is not on disk yet. I kept that (it is the check's purpose), so 'not failing while fuel/ is being written' is only true for files that are absent altogether. On the tree today fuel/ does not exist and 'sh bump.sh --check' passes with a 'skipped' line.
- sw.js no longer stores or serves vendor/zxing/*, so lab/scan.html (a lab page inside the scope, offline.md section 7) loses its offline reader. Follows from SPEC 3.10; nothing else uses it.

### Where the spec was unclear or wrong, and what was done

- The Reset and Restore texts in fuel.js are true only with one signed-in phone. With a second phone signed in, a Reset is half undone: that phone keeps its diary, saved foods and saved meals (sync.md 4.6 says a day leaves a phone only through deletion records, and Reset writes none) and uploads them again, while targets, units, theme and body weight are reset on both. Evidence: tests/fuel-sync.js step 'Reset on one phone while another is signed in' prints 'the log is back on both and in the account; targets on both are now {kcal:null,…}, units lb, theme system'. With one phone the account is emptied and Restore fills it again (run 'one phone'). I did not change the text.
- sync.md 4.3 says the legacy merge takes the union of deletion records and filters the phone's days by it. That would delete an entry the phone holds whenever Overload's copy has a record for it. I followed SPEC section 6 ('the phone's copy wins by id') and the shell's import instead: the bootstrap only adds, and Overload's records are taken only for entries the phone does not hold.
- SPEC says deletion records are never pruned, but saved-food ids are reused and fuel.js drops the record when the food exists again. For other phones to follow, sync.js lets a saved food or meal beat its record only when its `used` time is later than the record. Two limits follow. A food made again under an old id but not logged yet is removed again if another signed-in phone still holds the record. And with two phones whose clocks disagree, a deleted saved food can come back. Neither can happen with one phone.
- Entries without an id in Overload's cloud copy are not brought across by sign-in. They cannot be merged by id, and an id made in sync.js would not match the one the shell's import gives the same entry, so it would be doubled. v2.8 never writes such entries; the clipboard and file routes carry them.
- sync.md 4.3 suggests a 'legacy: done' field in meta/fuel for first uploads of more than 399 days. Not built. Up to 399 days the first upload is one batch (the test checks 111 writes in one batch). Beyond that it is several batches, and a refused one is sent again a minute later by the same phone.
- sync.md section 6 point 3 proposes that the page fetch the Firebase files after serviceWorker.ready. I did it inside the worker's activate instead, started but not waited for, so the page needed no edit. If the browser stops the worker before the downloads finish, the files are stored at the next online start, as in v2.8.
- A limit that remains from v2.8 (sync.md 1.10 point 2): a phone that was offline sends its whole old documents later. Additions and deletions made meanwhile on another phone survive (tested), but an edit to the same saved food, meal, entry, targets or settings on the other phone is overwritten.
- Hazard 9 of sync.md holds for Fuel too: once meta/fuel exists, Overload's copy is never read again. If Fuel signs in before Overload has uploaded everything, or the account has no foodDays at all, the missing days come only by Copy my food log. Tested for the no-days case: saved foods, meals and targets arrive, Settings still offers to bring the log, and the paste then uploads 110 days without doubling anything.
