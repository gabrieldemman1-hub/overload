# Split and redesign: the spec (final for 3.0)

The owner asked for two things:

1. Split Overload into two separate apps: a training app and a diet app. Keep all current data and separate it between the two.
2. Revamp the design.

One person uses the app, on an iPhone, from the Home Screen. Their only copy of the data may be the installed app's localStorage (cloud sync is optional; we cannot know whether it is on). The first rule of this change:

> **Nothing in this change may delete or rewrite data the owner already has.** The training app keeps carrying the food data it holds today until the owner removes it on purpose. A roll-back to v2.8, or v2.8 starting again by itself during a half-arrived update, must find everything as v2.8 expects it.

The detailed findings behind every rule here are in the notes next to this file: `state.md`, `host-api.md`, `sync.md`, `offline.md`, `connector.md`, `ui-inventory.md`, `fixtures.md`. Where a note and this spec disagree, this spec wins; say so if you think the spec is wrong.

## 1. The two apps

| | Overload (training) | Fuel (diet) |
| --- | --- | --- |
| Address | `/overload/` (repo root, unchanged) | `/overload/fuel/` (new folder `fuel/`) |
| Home Screen icon | the installed one keeps working (iOS keeps its old picture) | new: added from Safari |
| Page | `index.html` | `fuel/index.html` |
| Main script | `overload.js` (it was `app.js` up to 2.8; see below) | `fuel/fuel.js` |
| State key | `overload.state.v1` (unchanged, `v: 1`) | `fuel.state.v1` (`v: 1`, `app: 'fuel'`) |
| Other keys | `overload.sync.v1`, `overload.backup`, `overload.theme`, `overload.conn.*` (all unchanged) | `fuel.sync.v1`, `fuel.backup`, `fuel.theme` |
| Automatic copies (IndexedDB) | `overload-copies` (`backup.js`) | `fuel-copies` (`fuel/backup.js`, its own copy of the file) |
| Offline cache | `overload-vN` | `fuel-vN` (never a name starting `overload-`: the root worker deletes those) |
| Service worker | `sw.js`, scope `/overload/` | `fuel/sw.js`, registered as `./sw.js` from the Fuel page, scope `/overload/fuel/` |
| Files with `?v=` | answered from `overload-vN` for the whole release; the network only when the entry is missing | the same, from `fuel-vN` |
| Release marker | `const VERSION = '3.0'` in `overload.js` and `release: '3.0'` in `sync.js`, each exactly once; the first line `/* release 3.0 (…) */` in every other versioned file (shared ones included) | `const VERSION = '3.0'` in `fuel/fuel.js`, exactly once; the first line `/* release 3.0 (…) */` in every other versioned file |
| Manifest | `manifest.webmanifest`: `start_url`, `scope` and no `id`, exactly as today | `fuel/manifest.webmanifest`: `start_url: "./index.html"`, `scope: "./"`, no `id` |
| Cloud sync | `sync.js` (patched), Firebase default app, `meta/state` + `workouts` | `fuel/sync.js` (own copy), Firebase app named `fuel`, `meta/fuel` + `fuelDays` |
| Tabs | Today, Program, Exercises, History, Settings (screen names unchanged) | Today (screen name stays `food`), Trends, Settings |
| Version | 3.0 | 3.0 (always released together; `bump.sh` bumps both) |

Shared by both apps: `shared/ui.css` (the design system) and `shared/icons.js` (the icon set); used by Fuel from outside its folder: `data/foods.json`, `vendor/zxing/`. Nothing else is shared; each app is otherwise self-contained in its folder.

The root names `app.js`, `styles.css` and `food.js` stay unused (`bump.sh` fails when one exists). v2.8's stored page asks the server for them; with nothing there, v2.8's worker answers with its own stored copies, so a v2.8 page never runs 3.0's main script, stylesheet or food code (review findings U1, U2). `sync.js`, `connector.js`, `programs.js` and `backup.js` keep v2.8's names, so a v2.8 page can get 3.0's copies of those: `tests/train-sync.js --base=v28` and `tests/train-backup.js` run that combination.

Both workers answer a same-site address with `?v=` from their own cache, so the files of one release are the ones it installed, whatever the server (which ignores `?v=`) hands out later. Pages, unversioned files, `?db=` and the Firebase SDK stay network-first. The install is all or nothing: it refuses a page that does not ask for this release's files and every versioned file whose release marker is not this release's, stores nothing before every file has arrived, and writes the entry `installed` last. At run time a versioned file from the network that names another release (or none) is answered with a 409 and not stored; for a main script the start-up rescue then takes over, which uses only a cache holding `installed`. A network page of an older release is answered with the stored page (`offline.md`, sections 10 and 11).

"Fuel" is a working name. Keep it in as few places as possible (manifest, page title, top bar, a constant `APP_NAME` in `fuel/fuel.js`, the wording in Overload's hand-over card).

Paths that must not move or change: `sw.js`, `manifest.webmanifest` fields, `data/foods.json`, `tools/*`, `connector/**`, `connector.json`, `.nojekyll`, `.github/workflows/*`. Do not touch `connector/` or the workflows at all (a change there can start a deploy).

## 2. Who owns which data

- **Training (Overload):** settings (all of them, including connector settings and `reminders`), exercises, presc, program, workouts, active, bodyweight, sleep, templates, deleted.bw / deleted.sleep / deleted.workouts, libVersion.
- **Food (Fuel):** food.targets, food.foods (favourites, recents, last amounts, barcodes and custom foods are fields on these), food.meals, diary, deleted.food.
- **Copied once, then independent:** settings.units, settings.theme, and the latest body weight (Fuel uses it only for the protein guide under the targets). Nothing else from `settings` may ever reach Fuel: `settings.connKey` is a secret.
- Weigh-ins, sleep and the morning check-in stay in Overload.

Fuel's saved state keeps today's field names so `food.js` runs on it unchanged:

```js
{ v: 1, app: 'fuel',
  settings: { units: 'lb' | 'kg', theme: 'system' | 'dark' | 'light' },
  food: { targets: { kcal, protein, carbs, fat }, foods: { id: food }, meals: { id: meal } },
  diary: { 'YYYY-MM-DD': [entry] },
  deleted: { food: { entryId: ms }, foods: { foodId: ms }, meals: { mealId: ms },   // never pruned in Fuel
             fav: { foodId: ms }, custom: { foodId: ms } },   // only once there is one (section 4, Deletions in Fuel)
  bodyweight: [ { date, weight } ],        // at most one item: the number used by the protein guide
  moved: { from, at, days, entries, madeAt } | null }   // record of the hand-over from Overload
```

A Fuel state, file or payload must never contain an `exercises` field (Overload's Import accepts any file with `v: 1` and an `exercises` array and replaces everything).

Fuel's own `normalize` guarantees every container above exists, coerces entry numbers (`kcal`, `p`, `c`, `f`, `at` to numbers, `meal` to 0..3), gives every entry an id, drops day keys that are not `YYYY-MM-DD`, and keeps unknown fields.

Changed:

1. **No Food.** No Food tab, no `food.js` script, no food card in Settings. `state.food`, `state.diary` and `state.deleted.food` stay in the saved state as "the old food copy"; `normalize` keeps handling them; no code changes them except rule 5.
2. **First 3.0 start.** The raw text of `overload.state.v1` is read before this version saves anything and stored with `window.__overloadBackup.take('split', raw)` (id `before-split`, never pruned and never written over; v2.8 lists and restores it). `split.at` (see 4) is recorded once the copy is known to be stored; the copy store gets a second try 5 s later, and a start cut short tries again at the next one.
3. **Hand-over card: "Food has moved to Fuel".** On Today until hidden, and always in full in Settings > Food. Hiding records the food data's fingerprint (`split.dismissed`), so the card comes back to Today when the old food copy changes. The full card offers, in this order:
   1. *Get Fuel*: a button that opens the Fuel address in Safari (`x-safari-https://` + host + path on iOS standalone; a normal new-tab link elsewhere) and a *Copy link* button, with the two instructions "In Safari tap Share, then Add to Home Screen".
   2. *Copy my food log* (clipboard) and *Save as a file* (share sheet, falling back to a download). A sheet that is cancelled or refused (`AbortError`, `InvalidStateError`, `NotAllowedError`) saves and counts nothing; any other share failure gives the download but does not count it; with no sheet the download counts; a second tap while a sheet opened in the last 60 s is still open does nothing (`shareFile`).
   3. In Fuel: *Paste from Overload*.
   4. A line for cloud-sync users, always the same: "Using cloud sync? Copy the food log or save it as a file from here as well. Signing in to Fuel with the same email may bring some of it across, but not always all of it." (This app no longer uploads food, and Fuel reads Overload's account copy only at its first sign-in.)
   5. *Remove the old food log from Overload*: see rule 5 (Settings only).
   The card shows what the copy holds (days, entries, saved foods, size). Once the last copy or file holds what is here now, Today shows a short card instead, until it is hidden: the title, "Copied. Open Fuel and tap Paste from Overload." (or "Saved as a file. Open Fuel and tap Choose a file."), Get Fuel and Copy link, *Copy again* (or *Save again*) and "This card is also in Settings, under Food." It is about as tall as the full card's step, so the second tap of a double tap lands on the card. When the old food copy changed after the last copy or file (v2.8 can run again during a half-arrived update), the full card comes back and says so.
4. **Per-phone bookkeeping** lives in the `overload.backup` localStorage object (unknown fields survive v2.8), never in the state: `split: { at, copied: { at, hash, days, entries }, filed: { at, hash }, removed: { at }, dismissed: <hash> }`. When storage is full it is held in memory for the session (`ui.splitHeld`), so the card still says what was done.
5. **Remove the old food log.** Offered in Settings only, and only while the last copy or file made on this phone holds what is here now. The first question names the removal copies that are let go (see below); it asks twice. Then it takes a safety copy of the whole state (`take('foodremove', text)`, id `before-foodremove-<ms>`: one per removal, the newest 3 kept, `KEEP_REMOVALS`); if that copy cannot be stored, or the food data changed meanwhile, nothing is removed. Then it empties `state.diary` only, takes the removed days off `overload.sync.v1`'s `days` (`forgetSyncedDays`) and records `split.removed`. `state.food` (the small catalogue) and `state.deleted.food` stay, so the cloud's legacy copy and a v2.8 roll-back stay sane. While signed in, it refuses beside a sync module of another release (`window.__overloadSync.release` differs from `VERSION`: "Finish the update first: open Overload once with good signal, then try again."), checked before the questions and again after the safety copy.
6. **Reset, Import, Restore** never drop the old food copy. Each of its two parts (the log with `deleted.food`; the saved foods and meals with the targets) is carried across when the phone holds it; the file's or copy's part is used only when the phone has none of it, and the question says which comes from where. Restore of the copy taken at the split or before a removal, while the phone holds food days again, puts the two logs together (`mergeDiaries`: the phone's entries as they are, the copy's added when the phone neither holds nor deleted them). The questions no longer say the food log or the account's food is erased. Import and Restore refuse a file that has `app` or `kind` set ("This is a Fuel file. Open it in Fuel."). Signed in, the questions end with `cloudNote`: the training data in the account is erased (Reset) or replaced (Import, Restore) too, and the food log in the account is not changed. Because these write no deletion records and the other phone's are merged in, another phone signed in to the account sends back the weigh-ins and nights it logged or changed since it last synced (since review round 3, sync#3; a phone still on 2.8 sends back all of its own, after Import and Restore those for the dates the file or copy does not have), and after Import or Restore it deletes again any workout, weigh-in or night its deletion records name (the last 90 days). A workout in progress on the other phone stays there and comes back (code#4); on a phone still on 2.8 it is lost. The questions say so and give the way out: sign out on that phone first and reset it before it signs in again (`tests/train-cloud.js` runs each part with two phones). Signed out, the three remove `overload.sync.v1` (`forgetCloudIfSignedOut`). Before the sync module has said who is signed in (it has not loaded on this start, or Firebase has not answered), a note that names an account counts as signed in (`cloudAccount`), unless `overload.backup`'s `signedOut` names that account (the module's last word on this phone; `state.md`): the questions then end the same way, with "your account" (the note holds no email), and the note stays, so the next link sends the change (review finding sync#2). The sign-out question says what a later sign-in does: what was logged meanwhile is sent, a Reset, Import or Restore meanwhile is not (look#1). Since review round 3 the three also wait for their copy ("Before reset", "Before import", "Before restore"; `copyFirst`, as in Fuel): when it is not stored nothing is replaced or erased and a sheet offers Export ("The automatic copy could not be stored, so nothing was replaced. Export a backup first, then try again."; "erased" for Reset); when the data changed meanwhile, the toast says so and nothing is done (data#1, code#3). A second tap while one of them, or Remove, is under way does nothing (code#2). Reset erases the settings too, the WHOOP link included, as every version before; its questions say so (look#5), and it stops a running rest or cardio timer. "Replace everything" is asked only when the phone holds no food at all (code#6).
7. **Export JSON** is unchanged (whole state, old food copy included).
8. **Reminders:** the Food row is gone; the config sent to the connector always has `reminders.food.on = false` and no `done.food` (`connector.md` section 2.2). `settings.reminders.food` stays in the saved state.
9. **Cloud sync:** the patch in `sync.md` Appendix A: never read, write, merge or delete `foodDays`; re-send the food part the cloud already holds; send the core only after the cloud's core was seen in the session. Since the fixes (S1, S5; `sync.md` 1.1, 1.4, 1.5): the note keeps `parts` beside `core`; the core goes only when this phone changed a training key or a deletion record younger than 90 days, and the first core of a session only after the server's own core was taken in; a merge keeps this phone's value only for the keys it changed, and for weigh-ins and nights (review round 3: sync#3, sync#4; the note's parts hold a hash of each date) only for the dates it added or changed: for every other date the cloud's entry, or its absence, stands. The workout in progress on this phone stays when another phone resets, imports or restores (code#4). At start, `load()` removes `overload.sync.v1` when `overload.state.v1` is missing or empty (S2), so the next sign-in is a first link. `sync.js` exposes `release: '3.0'` (rule 5).
10. **Service worker:** the fetch handler returns early for `fuel/`, `data/` and `vendor/`; `food.js`, `data/foods.json` and `vendor/zxing/*` leave the install list; `notificationclick` ignores windows under `fuel/`; the page holds a pending reload while a sheet is open as well as during a workout or typing. Files with `?v=` are cache-first and the install checks the release markers (section 1).
11. **Start-up rescue** (inline script in `index.html`): falls back only to an older release of this app with the same major version, matches the full path of this app's scripts (the main script is `./overload.js`), and handles every stylesheet link.
12. **Timers across a reload.** A running rest or cardio timer is kept in `sessionStorage` (`overload.timer`: end, total, kind, next, and the workout it belongs to) and started again at the next start of the same session, so "Update ready" mid-workout does not drop it; a cardio timer that ran out meanwhile logs the cardio. v2.8 kept the timer in memory only, so the update from v2.8 itself cannot keep it.
13. **Automatic copies** (`backup.js`, still under v2.8's name): each removal has its own copy (rule 5); a lost IndexedDB connection is let go and opened again (an iPhone drops it for an app back from the background), and a failed transaction is tried once more on a fresh one. Remove refuses when the list of copies cannot be read ("The automatic copies could not be read, so nothing was removed. Try again."), as its question could not say which copy is let go; it names a copy let go by its date, and its time too when another removal copy is from the same day. (look#2, code#5).

## 4. Fuel 3.0

- `fuel/fuel.js`: a classic script that runs before `fuel/food.js` and offers what `food.js` takes from `window.__overload` (`host-api.md` section 8 and 12): `state`, `screen` (exactly `'food'` while the diary is on screen), `saveFailed`, `save()`, `render()` (synchronous), `lib` with the twelve helpers, plus what `fuel/sync.js` needs (`setState`, `unreadable`, `safetyCopy`, `setSyncStatus`, `syncChanged`, `startedWithData`) and the `overload:save` / `overload:sheetclose` events with their current names. Twelve members in all, nothing else (`tests/fuel-shell.js` checks the list).
- **Saved data and cloud sync's note.** `load()` sets `startedWithData` before anything can be tapped: whether `fuel.state.v1` held anything. When it holds nothing, or cannot be read, `load()` removes `fuel.sync.v1` (a note beside missing data would make the next upload delete in the account what it lists). `fuel/sync.js` believes a note only on a page that started on saved data: it may load seconds later, after Start fresh has saved an empty diary (review finding S2).
- `fuel/food.js`: moved from the root with `git mv`; the three page-relative addresses become `../data/foods.json?db=5` and `../vendor/zxing/...`. Further edits only where the redesign needs them (icons, markup classes), never to its data handling.
- Screens: Today (the food diary), Trends (new, read-only: 14 days of calories against the target, averages for this week and last week, days logged), Settings (targets, body weight for the protein guide, units, appearance, backup with automatic copies and export/import, cloud sync, About with the version).
- Robustness copied from Overload: the save-failed banner, the unreadable-data screen, storage use, automatic copies (one a day kept 7 days, refreshed when the app goes to the background so the day's food is in it; plus the latest one of each kind from before an import, a reset, a restore and a cloud first link that brings data in), the update flow, the start-up rescue.
- **The copy comes first** (review finding F1). Reset, Restore and an import wait for their automatic copy, as their questions say it is kept: when it cannot be stored (IndexedDB does not answer, or refuses it), nothing is erased, replaced or added, and a sheet offers Export; when cloud sync changed the data while the copy was being stored, nothing is done either. The copy before a cloud first link is taken from the data as it was before the account's is merged in; the sign-in does not wait for it.
- **Offline status** (O3). Until Fuel's own worker is active, Settings > About says "Getting ready to work offline…" (it is installing) or "Not ready to work offline yet. Open Fuel again with good signal." (there is none). A first install that failed is registered again each time the app comes back to the front.
- **Where it runs on an iPhone** (`'standalone' in navigator`):
  - not standalone (a Safari tab): show "Add Fuel to your Home Screen" (Share, Add to Home Screen) with a quiet "Use it here anyway". When the tab already holds Fuel data (he went on here before), say so first and offer Export: the Home Screen app starts empty, and its Welcome takes that backup under *Choose a file* (F2);
  - standalone, `overload.state.v1` present and no `fuel.state.v1`: this is Overload's own storage. Show the same instructions with *Open in Safari* and *Copy link*; take no data and do not register the worker.
  - otherwise run.
- **Welcome** (no Fuel data yet): *Paste from Overload*, *Choose a file*, *Sign in to cloud sync*, *Start fresh*; and, when this browser's storage holds `overload.state.v1` with food in it (desktop, Android), *Bring it from Overload on this device* first.
- **Import** accepts: the clipboard text, the food file, a full Overload backup (`v: 1` with `exercises`: only the food part, `settings.units`, `settings.theme` and the latest weigh-in are taken), a Fuel backup. It never removes, and adds only what is missing, with one exception for saved foods (`planImport` in `fuel/fuel.js`; review findings H1, H4, H5):
  - entries by day and id: an entry is already here only when Fuel holds its id on that same day (Fuel's copy then stays; before v2.5 an entry edited across midnight was kept on both days under one id, and v2.8 shows both). New entries go at the end of their day. An entry without an id gets one made from its day and what it holds as it arrived (identical ones on a day are counted), so a later copy does not add it again;
  - saved foods by id: Fuel's stays, and takes the copy's star when it has none. When the copy's is one he corrected or typed in (`src: 'custom'`) and Fuel's is the food list's own (`src: 'usda'` or `'off'`), the copy's whole food takes its place, with Fuel's `used`, `last` and star kept. A food that is `src: 'custom'` in Fuel keeps its numbers (it can still take the star). Not the star of a food Fuel has a `deleted.fav` record for, and not the copy's `src: 'custom'` food when Fuel has a `deleted.custom` record for it (review findings data#3, data#4; `addFromOverload` in `fuel/sync.js` the same). The question names these ("2 saved foods updated from Overload: the favorite star, your corrected numbers.");
  - saved meals by id (Fuel's stay); targets and body weight only when Fuel has none; units and theme only at Welcome;
  - Fuel's deletion records respected (by id, on every day); the copy's records come along for anything Fuel does not hold.
  It shows what will be added first, takes a safety copy and waits for it (see above), records `moved`, and warns when the payload is not newer than the last one imported.
- **Deletions in Fuel** are recorded for entries, foods and meals and never pruned, so a later import or cloud bootstrap cannot bring them back. Two more records exist once there is one, so a state without them is stored as before: `deleted.fav[id]`, a star he took off (the star button, or deleting a starred food), dropped wherever the food is starred again (`dropStars`, at every save and in `normalize`); and `deleted.custom[id]`, a `src: 'custom'` food deleted with "Delete this food", which stays when the food list's copy is logged again (that drops the `foods` record). Both are exported, kept in the copies, brought by a Fuel backup, and synced in `meta/fuel`'s core like the others.
- **Words** (review round 3, look#1, #4, #5, #11): Welcome promises one step for Paste and a file, and says signing in may bring some of the log across, but not always all of it; Settings > From Overload and the import sheet say "Only what is missing here is added, with the favorite stars and the numbers you corrected in Overload. Nothing else is replaced or removed.", and Settings > Backup the same for any file; Reset names everything it erases ("…targets and settings in Fuel on this phone, body weight, units and theme included?"); the sign-out question says what the next sign-in does with what was logged and with a Reset or Restore done meanwhile; without the sync module the card says "Cloud sync is not available right now. It starts when the app opens with signal. Your food log stays on this phone."
- **Export** goes through `shareFile` as Overload's: a second tap within 60 s of a sheet that is still open does nothing, a later one goes through (code#1); a failure other than a cancel or a refusal offers the download without counting it as an export. `fuel/backup.js` gives up a transaction that has not finished in 5 s (`RUN_WAIT`, data#2), so Reset, Restore and an import then say the copy could not be stored, and work again afterwards.

## 5. The hand-over payload

```js
{ kind: 'overload-food', v: 1, madeAt: <ms>, from: 'Overload 3.0',
  food: { targets, foods, meals }, diary: { 'YYYY-MM-DD': [entry] }, deleted: { food: { id: ms } },
  settings: { units, theme }, bodyweight: [ latest weigh-in ] or [] }
```

- The diary is copied as it is (entries whose food no longer exists and quick adds included).
- Clipboard text: `OVERLOAD-FOOD:1:` + base64 of the gzip (CompressionStream) of the compact JSON as UTF-8 bytes; `OVERLOAD-FOOD:0:` + base64 of the UTF-8 bytes when gzip is not available. Never `btoa` on the raw string (names hold non-Latin-1 characters).
- File: `overload-food-YYYY-MM-DD.json`, the compact JSON, made at the tap.
- Overload makes the clipboard text ahead, when a card with the Copy button is drawn (an iPhone lets a page write to the clipboard only during the tap, and gzip takes longer), and makes it again whenever anything the payload holds changes: the food data, the latest weigh-in, units, theme, the food deletion records. `madeAt` is when that text was made. A tap before the text is ready hands the clipboard a promise of it.

## 6. Cloud sync

Firestore today: `users/{uid}/meta/state` (`core`: one JSON text of settings, exercises, presc, program, active, bodyweight, sleep, templates, food, deleted), `users/{uid}/workouts/{id}`, `users/{uid}/foodDays/{date}`.

- **Overload 3.0:** `sync.md` section 3 and Appendix A, and the fixes in section 3 rule 9 (`sync.md` 1.1, 1.4, 1.5, 1.10). The note `overload.sync.v1` gains `parts` (`state.md`); v2.8 keeps it unchanged.
- **Fuel:** `sync.md` section 4. Owns `users/{uid}/meta/fuel` (`core`: JSON text of settings, food, deleted, bodyweight) and `users/{uid}/fuelDays/{date}`. First sign-in when `meta/fuel` does not exist: read `meta/state` and `foodDays` once, read-only, take the food part, add it to what the phone has by the rules of an import (section 4; `addFromOverload` in `fuel/sync.js` repeats them, with units and theme taken when the phone holds no food yet, as signing in from Welcome leaves Welcome before the account answers, and entries without an id left out), keep the copy "before cloud" of what the phone held (not waited for), then write only its own documents. Signing in and Paste from Overload of the same log, in either order, end byte for byte the same in the diary and the saved foods, and the second finds nothing new; on an account without food days the sign-in takes none of Overload's deletion records for that (review finding sync#5). It never writes under `meta/state`, `workouts` or `foodDays`.
